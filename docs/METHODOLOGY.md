# 题库研究与排序方法

## 目标和边界

题库服务的目标岗位是 Java 后端与 AI / Agent 应用开发的实习、校招和 0–1 年经验职位。它回答“在当前收录的公开证据下，初学者应先练什么”，不声称统计了全互联网，也不把公开帖子数量解释为真实录取概率。

快照日期：2026-08-29。重新调研时应更新 `research/sources.json` 的快照日期和每个来源的发布日期。

## 来源分层

从高到低使用以下证据：

1. 近期真实面经：明确公司、轮次或岗位，正文包含直接问题；这是排序的主要信号。
2. 近期多公司复盘：用于发现跨公司共性；含推广、疑似加工答案或公司标注冲突时降权并写入备注。
3. 公开岗位要求：验证招聘方明确要求的语言、框架和工程能力，不作为某道原题出现的证明。
4. 持续维护的面试指南：交叉验证稳定基础并补齐知识结构，不能压过最新面经。
5. 公开题库关注度：只读取公开榜单、热度、题目标题和链接，用于识别用户正在关注的知识点；不访问 VIP 答案，也不计作真实面经。
6. 官方文档和研究：校验接口与技术事实，不用于制造“高频”印象。

转载内容尽量回溯原帖。同一内容指纹簇最多计一次；多公司汇总、题库整理和推广内容标为聚合来源并按 0.32 倍计入，不能通过转载或一帖罗列几十个知识点抬高权重。

## 数百样本的采集与分析

1. 只从平台公开 Sitemap 增量发现候选，不抓取牛客禁止的搜索页，也不绕过小红书的普通自动抓取限制。
2. `discuss` 与 `feed/main/detail` 两类入口分别排序并交错进入有限扫描窗口，避免单一 URL 形态挤掉另一类样本；本地再提取主帖、按中国时区校验正文发布日期、计算内容指纹、识别直接问题信号并匹配已有知识点。这一步不调用 AI，Sitemap `lastmod` 只辅助候选排序，绝不冒充发帖日期。
3. 高置信已有知识点直接形成证据。低置信或疑似新概念的来源才按约 8 篇一批提交给 AI；模型必须为每个概念返回当前正文中的连续 `evidenceQuote`，本地确认原文归属并用概念名称/同义标签校验映射后，结果才可进入私有缓存。
4. 批次中的缺失项或全部被证据校验拒绝的来源只做定向单篇复核；单篇遇到超时、格式错误或无证据映射时使用压缩正文重试一次。连续 3 个完整批次在重试后仍不可用会打开熔断器，剩余来源直接走单篇，避免弱模型反复消耗长批次调用。
5. 缓存键同时包含正文哈希、分析模式、候选概念目录和 Prompt 版本；未变化的第二次更新不重复调用 AI。Prompt/证据规则版本变化会使旧缓存整体失效，防止历史无证据结果继续复用。
6. 小红书 Sitemap 只有 URL、没有可用标题/日期。未通过用户登录浏览器或用户提供的明确链接核验前，只能算候选，不能伪装成有效面经样本。
7. 默认从最多约 1.35 万个近期 Sitemap 页面收敛 300 篇样本。发现缓存保存最多 3 万条版本化预筛结果并每 1000 页原子落盘；规则版本变化时主动失效旧结果，普通增量更新则只访问新 URL。

## 去重与拆题

先把近义问法归并为“概念”，例如“HashMap 为什么线程不安全”和“并发写 HashMap 有什么问题”归到 HashMap。再对每个概念生成五种独立训练角度：

- 定义：是什么、解决什么问题。
- 机制：内部过程和因果链。
- 应用：项目中如何设计和验证。
- 故障：错误现象、原因和排查。
- 对比：与相邻方案如何选型。

内置目录以 100 个后端概念和 40 个 Agent 概念为稳定基线；当前为 145 个后端概念和 52 个 Agent 概念，共 985 个可独立作答的问题。题库容量目标约 1000 题：数百篇新样本默认只更新证据、趋势和排序，不线性增题。新概念必须先进入 `research/concept-candidates.json` 观察池，达到至少 3 个近期独立直接面经以及公司/平台多样性门槛，且仍有容量配额，才可每轮最多晋级 3 个概念（每个 5 题）。动态概念保持追加式顺序，不能插入内置目录或重排旧条目，以保护既有题目 ID 和浏览器学习进度。

Java 后端采用主流八股站点常见的同级专题：Java 基础、Java 集合、Java 并发、JVM、Spring 生态、MySQL、Redis、计算机网络、操作系统与 Linux、消息队列、分布式与微服务、系统设计与场景。每个专题再维护二级知识组和具体知识点；五类问法是跨专题筛选维度，不作为知识目录父级。分类迁移只改变元数据，不改变概念顺序和稳定题目 ID。2026-08-28 的覆盖审计及具体 URL 见 [COVERAGE_AUDIT.md](COVERAGE_AUDIT.md)。

增量更新时，内置概念和此前由更新管线加入的动态概念会一起进入同义归并；相同 URL 复用既有来源记录，新发现的支持关系补到来源与概念上，不用重复来源或重复概念制造频次。一次只能运行一个分析任务，取消会中断后续抓取与模型请求，并且不会留下可应用草案。

## 重要度计算

每个概念先由研究者给出 1–5 的岗位优先级。每道题的分数计算为：

```text
importance = min(98,
  46
  概念优先级 × 4
  + 考查角度奖励（2–5）
  + 饱和面经频次（最多 16）
  + 来源多样性（最多 5）
  + 岗位/资料交叉验证（最多 2）
  + 公开题库关注度（最多 2）
)
```

面经证据先按内容指纹簇去重，再乘来源质量、时间衰减和聚合帖系数。最终频次奖励使用 `16 × (1 - exp(-weightedSupport / 6))` 的饱和曲线，并按全局独立样本规模做轻量置信收缩。因此样本从 20 增至 200 会让统计更可信，但不会把重要度扩大十倍。

来源多样性由明确公司、平台和候选人阶段组成，最高 5；岗位、指南和官方资料只提供最多 2 分的交叉验证，不进入面经频次。

公开题库关注度使用 `research/public-question-signals.json` 的最新单次快照。当前快照记录面试鸭近 30 天 TOP50 题库元数据，并完整保存 Java 热门 200 题、AI Agent 50 题和大模型 370 题共 620 个公开标题。标题先按同义词归并到已有知识点；同一标题在同一题库只计一次，同一知识点在同一题库只贡献一次排名/热度强度，再经对数归一化和饱和曲线得到 0–2 分。一次快照只能标记为低置信，不能宣称“近期上升”；标题数据不能创建新概念、不能提高 `recentInterviewSamples`、`independentInterviewSamples` 或 `frequencyBoost`。

公式实现位于 `scripts/generate-questions.mjs`，生成结果分别保存独立面经样本数、全局样本数、频次奖励、`weightedSupport` 和 `publicQuestionAttention`，可以复算。

等级只是方便筛选：

- `core`：重要度 ≥ 88
- `high`：重要度 ≥ 74
- `extended`：其余

## 考察口径与学习位置标注（更新题库时）

- 高频排序以近期真实面经为主；同时要求 AI 结合 JavaGuide、面试鸭、小林coding 等八股网站交叉验证概念表述与覆盖面。
- AI 为每个知识点输出 `learningHints`：站点、对应章节名、直达链接（不确定的链接留空）。学习位置仅作学习辅助，不参与 importance 计算。
- 八股网站内容本身不作为「高频证据」登记来源，避免把教材覆盖率虚增为面试出现频率；两者在界面中分开展示（「高频证据」与「八股文网站对应章节」）。

## AI 提取的语义证据保护

- `evidenceQuote` 必须是当前来源相关正文中的连续原文，不接受概括、改写或跨段拼接；少于 4 个规范化字符、无法在原文定位的证据会被拒绝。
- 映射已有概念时，证据句还必须命中目标概念的名称或目录中登记的同义标签。正文只谈 HashMap、模型却映射到 B+ 树索引时，即使 JSON 完整也不会进入来源关系或缓存。
- 一个批次中有效概念会被保留，只有缺失或全部无证据的来源进入单篇复核，避免为了少量异常重跑整批。单篇复核仍不通过时，该来源明确失败，不以结构完整冒充分析成功。
- 更新报告公开本轮证据通过数、拦截数、定向复核数和熔断状态；证据句本身只保留在 `.local` 私有分析缓存中，不写入公开题库，也不复制整篇外部正文。

## AI 评分复核（更新题库时）

本地公式是基线，不是最终裁决。更新题库时，受影响的题目（新题 + 分数变化的旧题，最多 40 道，按重要度取前）会交给 AI 复核：

- **约束 skill**：公式规则、来源类型系数、层级阈值作为系统提示词的硬性约束。
- **边界**：最终分必须是 0–98 的整数，与基线差 ≤6；越界调整会被本地系统驳回并回退公式分。
- **理由**：每次调整必须给出理由（≤120 字），写入 `scoreNote`，并在更新报告展示「基线 → AI 最终」。
- **持久化**：调整记录保存在 `research/ai-scores.json`，重新生成题库时自动应用；若公式基线变化（来源增减），旧调整自动失效。
- **失败回退**：AI 复核调用失败时保留公式基线分，并在进度中标注。

每个分数要么来自可复算的公式，要么来自带理由、有边界的 AI 判断，二者都可在更新报告与题目数据中追溯。

## 证据标签

- `strong`：全局至少 80 个独立直接样本；该概念至少 8 个独立直接样本、近 90 天至少 4 个，并覆盖至少 3 家公司或 2 个平台。
- `medium`：至少 2 个独立直接样本，或有明确岗位来源，但不满足 strong。
- `foundation`：主要由基础指南或官方资料支持，或属于默认前置知识。

`recentInterviewSamples` 表示当前登记并关联到该概念的近期面经样本数量，不代表全网频次。用户界面应始终同时展示这一限制。

## 公司专项与样本趋势

- 只把“有 http/https 原文链接、有可核验发布日期、正文包含直接问题证据”的面经纳入趋势；手动粘贴且无链接/日期的材料可以辅助答案，但不提升近期频次。
- 先按 `concept` 和转载簇双重去重：同一概念的五个训练角度只计一次，同一经历的转载也只计一次；聚合帖显著降权。
- 近期窗口为快照日前 90 天，对照窗口为此前 90 天。趋势同时展示累计样本、独立明确公司数、最近观察日期、信号标签和置信度。
- 公司专项只使用能明确归属单一公司的直接面经；“多公司”“汇总”或公司标注冲突的来源不进入任何单一公司题单。只有全局独立样本达到 120、单概念累计至少 10 次、近期至少 5 次且来源多样性达标，才显示高置信度。
- 互动关注度仅接受页面正文明确出现的浏览、点赞、收藏、评论非负整数；缺失时显示未知，AI 不得补猜。
- 公开题库关注度与帖子互动关注度分开：前者来自公开题库标题/榜单，单快照低置信且最多加 2 分；后者来自真实面经页面明确互动数字。两者都不得伪装成面经出现次数。
- 八股、官方文档、研究资料不进入近期趋势。页面必须同时展示平台分布、日期范围、排除样本和限制，统一称为“可审计的已采集样本趋势”。

实现位于 `scripts/source-insights.mjs`，公开接口为 `GET /api/insights`。

## 高频证据与学习来源分离

`evidence.sourceIds` 只解释题目为什么进入题库和如何排序；`learningSourceIds` 用于给初学者继续学习。Oracle、OpenJDK、Spring、MySQL、Redis、Kafka、Netty、NGINX、Docker、Elastic、MCP、LangGraph 与 OWASP 等官方资料不会因为“权威”就被当作真实面试出现次数，也不会虚增高频标签。

## 质量控制

`npm run validate` 会阻止以下内容进入正式题库：

- 总数或两条路线数量错误；
- ID 或标题重复；
- 关键字段为空；
- 精简答案过短；
- 缺少至少两个评分点；
- 引用了不存在的来源。

`npm run test:coverage` 固定 12 个 Java 后端专题中的 123 个主流目录必备检查项。`npm run test:public-signals` 固定 620 个公开标题快照、范围排除、至少 99% 的范围内知识点映射、题库内去重、最多 2 分和零面经频次泄漏。`npm run test:performance` 另外用 300 个隔离样本证明：首次最多 38 个批量 AI 调用、相同内容第二次为 0 次调用，题量保持 985。`npm run test:resilience` 注入“HashMap 正文误映射 B+ 树”和持续非法批次，验证错误关系被拦截、只复核异常来源、连续失败熔断以及纠正结果二次全缓存。完整发布验证 `npm run verify` 会同时执行生成、数据校验、容量门槛、性能、语义韧性与覆盖回归。

“已人工复核”是显式状态，不由概念优先级自动推断。复核记录位于 `research/content-reviews.json`，按稳定题目 ID 保存日期、说明和核查来源；生成器只对有效登记输出 `contentStatus: reviewed`，校验器会阻止不存在的题目、非法状态、缺失来源、批次数量不一致或生成状态不一致。当前前两批覆盖最高排名的 40 个核心概念，其定义和机制共 80 题。

自动检查不能替代事实复核。新增内容时，优先逐题复核 core 题，再处理 high 和 extended；变化快的模型接口、框架和协议还应复查对应官方文档。

## 已知偏差

- 公开面经由用户主动发布，岗位、地区、候选人背景和失败经历分布不均。
- 有的帖子包含二次整理或推广，来源权重已降低，但无法完全消除噪声。
- 一条帖子可能列出多个问题，当前版本记录“概念得到该来源支持”，没有抓取并保存网页全文或伪造精确词频。
- 公司面试会随团队和面试官变化；时间越久，排序价值越低。
- Agent 岗位仍快速变化，项目深挖、评测和工程可靠性通常比死背单一框架 API 更稳定。
